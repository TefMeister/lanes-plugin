# Changes

One line per version, newest first, in plain words: what it means for someone using the plugin.
**Every version bump adds a line here.** `tools/update-check.py` reads this file to tell users
what they are missing, and the smoke test fails if the newest line does not match `plugin.json`.
**The banner is fixed artwork and never changes on a release** (since 0.24.0). A new command goes on the
front page (`README.md` at the repo root); the smoke test fails if one is missing there.

- **0.52.0** (2026-10-08): **BeG0nE rides every session.** With `begone = <clone of the BeG0nE repo>` in lanes.conf, each session start makes sure BeG0nE's background rider is running and says in one line what it holds (VR sessions on file, behaviour patterns, the last one filed). The rider idles until a VR mod wired to BeG0nE's `jitterlog.h` starts a VR session, then collects what the mod did with the headset pose, the camera and the controllers, and files it with the cause of any stepping named; nobody is asked anything. BeG0nE's own code updates on its own; the plugin only knows where the clone is. Asked for by the maintainer.
- **0.51.0** (2026-10-08): **the plugin's look now shows the Lanes banner instead of the starburst.** Behind the text sits the Lanes Plugin banner, drawn in one dim, striped green with no white, so the letters stay easy to read; the rest of the green monitor is unchanged. A PC that already had the starburst is moved over once at the next session start; a look someone picked themselves is left alone. Style `theme/green-monitor-lanes/` (also in the terminal-themes repo), `tools/theme.py upgrade`, tests in `tools/tests/hooks-test.sh`. Asked for by the maintainer.
- **0.50.0** (2026-10-08): **a green tick says when you can stop holding.** Whenever a test needs the person to hold something (controllers up, the rifle on the sky, a pose, a button), the session prints `✅ **You can stop**` as its very first line the moment it has what it needs, before it reads or thinks about anything. Asked for by a user who kept holding a pose in the headset with no way to know whether the session had enough.
- **0.49.0** (2026-10-07): **menus are driven fast.** `/lm` now says: short gaps between menu presses (0.2–0.5 s), skip intros with the app's own keys, look at the screen only before destructive choices or when unsure, and wait for panels to stop animating before clicking. Driving directly is the default; Menu-o-matiC is for recorded routes. Asked for by a user watching a live session.
- **0.48.1** (2026-10-07): setup now finds DaVinci Resolve when it is installed on another drive, not only in Program Files.
- **0.48.0** (2026-10-07): **video tools in setup, and two more reply icons.** `/lanes:setup` now offers DaVinci Resolve (free) as the editor for progress videos, with FFmpeg beside it: Resolve runs without FFmpeg, but FFmpeg is what Claude uses on the recordings (cutting, joining, still frames, converting files the free Resolve will not open), so they are best installed together. Replies gain a fixed 🎬 **Recorded** heading and a 🎮 in front of each project's name when several are listed (`docs/PROTOCOL.md` §5). Asked for by the maintainer.
- **0.47.0** (2026-10-07): **a synced transfer folder for files that must not go on GitHub.** `/lanes:setup` now explains that some files (the app's own files, extracted assets, recordings, big builds) must never be uploaded, suggests a MEGA account as the most seamless way to carry them between your own PCs, reminds you that sharing game files with other people is illegal, and offers the steps to set up a synced folder with `Videos` and `Game Files` inside. Save it as `transfer = <folder>` in `lanes.conf` and sessions sort files into it. Asked for by a user who moves recordings and game files between two PCs.
- **0.46.0** (2026-10-06): **builds sorted by feature, and the app's original files kept safe.** `builds.py snap ... --feature "Ladder climb"` puts the build in that feature's own folder, so one feature's builds are easy to find apart from another's; the numbers still run in one sequence, and `features` and `list --feature` show them. New `builds.py vanilla <project> <path>` saves the app's own untouched copy of a file before a mod changes it, into `_vanilla/` (kept on the PC, never uploaded; only its hash list is shared), and `builds.py vanilla-restore <project> --yes` gives back the plain, working app at any point. `/lm` and `/ms` now snap with a feature and save originals first. Asked for by a user who wanted to be able to go back to a working game even late into modding. `docs/PROTOCOL.md` section 14; `builds-fixture.sh` now has 75 checks.
- **0.45.0** (2026-10-04): **breakthroughs are marked IMPORTANT in the session logs.** `session-log.py write ... --important` puts `IMPORTANT_` in the file name and a star line at the top, and `session-log.py important` lists only those, so the steps that really moved a project forward stand out from routine logs. Sessions mark one without being asked when the person says it finally works or a cause is found after a long hunt. Asked for by the user who asked for session logs.
- **0.44.0** (2026-10-04): **every session summary is kept, dated, one folder per project.** New `tools/session-log.py`: `write <project> <slug>` saves the summary from stdin as `<session_logs>/<project>/YYYY-MM-DD_HHMM_<slug>.md` and, when that folder is a git clone, commits only that file and pushes it; `list` and `search` find earlier ones. `/lm`, `/pd` and `/ms` save their write-up there before the close-out box, and a session that is stuck on a problem searches the logs before trying again. Set `session_logs = <folder>` in lanes.conf (keep the repo private); unset, nothing happens. Asked for by a user who wanted every summary kept and wanted them looked at when stuck. `docs/PROTOCOL.md` section 17, test `tools/tests/session-log-fixture.sh`.
- **0.43.0** (2026-10-04): **Mint is gone: modding happens in the app's own folder again.** The private-copy feature (`/lanes:mint`, `tools/mint.py`, the `mint_*` and `work_in_original.*` keys) is removed, at the request of the person who asked for it, unsure whether it was breaking things. `/lm` and `/ms` no longer check a clean install or switch to a copy; `builds.py` uses `builds_app.<project>` or the project's own `app` setting. Leftover `mint_*` lines in lanes.conf are ignored, so delete them. A copy folder made earlier stays on that PC until you decide; the plugin never deletes it. `docs/PROTOCOL.md` section 15 says what it was.
- **0.42.2** (2026-10-03): **the gate/model box moves down one place.** The write-up now opens with the close-out box, then the gate/model box, then the text, so the next step sits right above the instructions instead of above the save report.
- **0.42.1** (2026-10-03): **the write-up is boxes first, text last.** The gate/model box and the close-out box now open the session write-up and the text sections follow, ending on what is needed from the person, so the instructions sit at the bottom of the terminal instead of above two tall tables. Asked for by a user who had to scroll up every session. Docs only (`docs/PROTOCOL.md` section 5, `/lm` `/pd` `/ms`).
- **0.42.0** (2026-10-02): **`/lm` and `/ms` run the game from its private copy whenever one exists.** New `mint.py where <project>` names the folder a live session uses: the copy (`mint_copy`), or the game's own folder when the project carries `work_in_original.<project> = <why>` in lanes.conf, for games still at the reverse-engineering stage, until hands-on fine tuning begins. Asked for after a session had to be told which RE2 folder to use. Tests in `tools/tests/mint-fixture.sh`.
- **0.41.2** (2026-10-01): the handover light says when this PC's own copy of the board is DAMAGED, instead of "no remote" and "GitHub could not be reached". On 2026-10-01 the home PC's board clone had twenty-eight half-finished fetches and a remote ref pointing at a commit that never arrived; the light went red, which was right, but both of its reasons pointed away from the real cause. Now a clone that has a remote but cannot count against it is reported as `damaged clone (run git fsck in it, or clone it afresh)`, and a fetch that fails while GitHub still answers a plain listing is reported as a damaged copy, not as GitHub being away. Test in `tools/tests/handover-fixture.sh`.
- **0.41.1** (2026-10-01): the "Green Monitor Claude" tab opens on the Desktop (home folder if there is no Desktop), not in system32. Only a profile the plugin creates gets this; a profile you already had keeps its own start folder. When the plugin has to add that tab type, it now says so in plain words: the plugin comes with one look, and you find it by clicking the small down arrow next to the + in Windows Terminal. Also the theme test's helper functions, which 0.41.0 called without defining, so five of its checks had never run.
- **0.41.0** (2026-10-01): **the plugin's look: an old green monitor, a starburst behind the text and a light rolling down the screen.** This is how the plugin ships now. The first session after installing (and restarting Claude Code) puts the `green-monitor-starburst` style on the Windows Terminal profile Claude runs in: colour scheme, font (Share Tech Mono, installed for this user), cursor, padding, icon and the shader, plus the RobCo theme for Claude Code's own colours, which follow after a restart. The terminal's settings are backed up first, every previous value is kept, a profile that already has a look of its own is left alone, and `/lanes:theme restore` puts everything back. `theme = off` in lanes.conf stops it; without Windows Terminal it says so once. Tool `tools/theme.py`, hook `theme-apply`, files `theme/green-monitor-starburst/`, tests in `tools/tests/hooks-test.sh`.
- **0.40.0** (2026-10-01): **the close-out box: the end of every write-up, refurbished.** The report used to end with three pieces in three styles (a hand-written save table, the Inspector's sentence, the HANDOVER line in capitals). Now `handover.py close` prints one table in the same shape as the gate/model box, from facts, so no row can be faked: `SAVED` / `NOT SAVED` as the headline, a row per repo this session pushed (from a snapshot the session start takes), the Inspector's count, any claim still held, and when the other PC last saved. The headline word is the signal and the box prints after every session, so a read-only session no longer has to leave the table out for its absence to mean something. `docs/PROTOCOL.md` section 5; test `tools/tests/handover-fixture.sh`.
- **0.39.1** (2026-10-01): code tidy only, no change in behaviour: the handover light's time and length numbers are named settings (the Inspector asked).
- **0.39.0** (2026-10-01): **the handover light: is it safe to carry on from the other PC?** Every session now opens with three plain lines: whether everything on this PC is on GitHub (every clone in every lane root; a file never added, a change not committed or a commit on no remote branch makes it NOT SAVED and names the repo), when the OTHER PC last saved and how its last session ended (read from GitHub, never from this disk), and - with `handover.py fresh` - whether a clone root is behind GitHub (`--pull` brings it up, fast-forward only). The session's end reports this PC on the board, so the other PC is told if work was left unsaved. Every lane's write-up ends with the HANDOVER line; no line, no trust. Built after five helper scripts were found to exist on one disk only, and a summary had blamed the other PC for being away when this PC's own copy was behind. Tool `tools/handover.py`, hooks `handover-brief` / `handover-end`, test `tools/tests/handover-fixture.sh`, rule `docs/PROTOCOL.md` section 10.
- **0.38.0** (2026-09-30): **every session now ends with the Inspector's score.** One line at the end of each `/lm`, `/pd` and `/ms` report says how many messy spots the Inspector found in that session's code, and how many were fixed, kept on purpose, left for later, or are still unanswered, so you can see whether it is really taking part. Releasing a lane also shows the line on screen. It says "off" when the Inspector is off. New: `tools/inspector.py summary`.
- **0.37.1** (2026-09-30): wording only. The Inspector's design page (`docs/specs/inspector-idea.md`) no longer says it is an unbuilt idea; it now points at `docs/PROTOCOL.md` §16 for what it does.
- **0.37.0** (2026-09-30): **the Inspector: every piece of code Claude writes is looked over.** Optional and off unless you switch it on (`/lanes:setup` asks). After each code edit it notes anything messy - files past 800 or 1,500 lines, numbers and addresses written straight into the code, F-key hotkeys, probe code left in, commented-out code, very long or deeply nested functions, blocks copied from elsewhere - in a notes folder kept with the project. It never edits code. Saving is never blocked; uploading waits until each note has an answer (`fix now`, `fix later: <board row>`, or `keep: <why it must stay>`), and a copy of any held work is kept safe meanwhile. Only new or worse mess is raised. Tested in private on four projects before joining (`docs/PROTOCOL.md` §16).
- **0.36.1** (2026-09-29): the three menu goals are recorded in a fixed order: launch → gameplay, quit; launch → key bindings, quit; then into gameplay (goal 1 replays it) and out to the desktop. Each is replayed once before the next is recorded. First game done this way: Alan Wake, a whole round in 31 s.
- **0.36.0** (2026-09-29): **a simpler menu recorder, three keys.** Home starts recording (even before the game starts, so skippable logos are caught), Page Down means "the next key I press is a step" (a picture of the screen plus exactly that key), End stops. Nothing else is recorded, so stray presses never reach a route; if it goes wrong, record again. Each game gets three goals: launch → gameplay, launch → key bindings, gameplay → desktop. Designed by a user after a replay of the old shape got stuck on a load screen.
- **0.35.1** (2026-09-29): Menu-o-matiC now picks the **largest** window with a matching title. Some games open a tiny start-up window with the same name first (Enslaved's is 160×28), and a recorder attached to it saw nothing.
- **0.35.0** (2026-09-29): **Menu-o-matiC drives awkward games.** A route can send keys as window messages (`"key_input": "post"`) for games that ignore SendInput, press a launcher dialog's button (`--button Play --dialog ...`, BM_CLICK, ANSI-safe), tell two windows with the same name apart (`=TITLE` matches exactly), and close a game through WM_CLOSE (`{"close": true}`). First game: Manhunt, closed → playing in 22-25 s.
- **0.34.0** (2026-09-29): **Menu-o-matiC maps a game's menus, not just the way to gameplay.** Each route now has a start and an end (`--from closed --to keybindings`), `mom routes <folder>` lists a game's map, and a route can end with `picture` steps that save a settings page (the key bindings) to be read once and stored in the route as `controls`. Move-o-matiC follows the same idea with short named trips. First game: Prototype (closed → gameplay 62 s, closed → key bindings 65 s with two pictures).
- **0.33.1** (2026-09-29): **the window is confirmed once per game, not every session.** After the person says yes, `mom windowcheck <window> --route <route.json> --confirmed` stores it in the route; later checks only measure and ask again only if the window changed size or turned fullscreen.
- **0.33.0** (2026-09-29): **no modding until the person confirms the game is in a proper window.** `/lm`, `/ms` and `/lanes:menu` now make a fixed window the first job and then ASK the person whether the game is windowed, the right size, and whether they can still see the session beside it; their answer settles it, and if the check cannot tell, they are asked whether it is windowed at all. A fullscreen game hides the session from them. New `mom windowcheck <window>` measures the window AND the screen, because a game told only a size can switch the whole display and run fullscreen while its window measures exactly right (it happened with Prototype). `record` prints the same check before recording.
- **0.32.5** (2026-09-29): **a game's first menu recording starts with a rehearsal.** The person launches the game once themselves and plays the route with nothing recording, noting every button each screen needs; only then is it recorded, so the recording has no mistaken presses or guessing. `record` reminds you when a route has no keys yet, and `/lanes:menu` says it.
- **0.32.4** (2026-09-29): Menu-o-matiC and Move-o-matiC can now press numpad plus, minus and star (`numpadplus`, `numpadminus`, `numpadstar`), which many mods use as hotkeys.
- **0.32.3** (2026-09-29): **a replay no longer stops when a game opens its window empty for a moment.** Alice: Madness Returns does that at start-up, and the replay quit with an error instead of waiting; it now keeps waiting (and finds the window again if the game swaps it for another). Alice's menus then replayed from a closed game twice, 50 s each.
- **0.32.2** (2026-09-29): **the recorder's marker keys moved off the number pad**, to Page Up (a key is needed on this screen), Page Down (just wait), Home (undo the last mark, new) and End (stop). Our own mods keep their hotkeys on the number pad, so a press that reached the game moved a mod's view mid-recording. Only the grey keys count; the number pad with NumLock off is recorded as ordinary keys.
- **0.32.1** (2026-09-29): **Move-o-matiC says what a recorded drive is FOR before you play it.** New `brief` command: a route can carry a short sheet (what the test is for, where to start, each move in order, what must stay on screen, what to avoid, how to end), and `record` prints it before recording starts, so the person plays what the test needs instead of a drive that merely happened. Asked for on the first Burnout drive, which was recorded before anyone had said what it was for. The setup guide also now says to check that a save really loads in the same spot, and to put checkpoints on things that do not change with the game clock.
- **0.32.0** (2026-09-29): **going back to an older build on purpose no longer sets off a warning.** Test builds that did not work are taken back out of the app folder, so it often holds an older build than the newest one saved, and the session-start check kept asking for the newest back at every start although nothing was wrong (six failed test builds made it ask for the last of them, on the very PC that made them). New `builds.py back <project> <N> "<why>"` (or `restore ... --why "..."`) notes that staying on build N is deliberate, in `<project>/HELD.txt`, pushed so the other PC knows too. The check then stays quiet, and `which` says it is on purpose. A build saved AFTER the note is still reported, because that one may really be missing. `builds-fixture.sh` now has 46 checks.
- **0.31.4** (2026-09-28): **the top of a board gets checked too, not only its to-do list.** At the end of a session, `/lm`, `/pd` and `/ms` now also read the lines above the `OPEN` block (where the project is cloned, which PC has what) and fix anything the session found untrue. A board kept saying one PC had no copy of a project for eight days after it did, because only the to-do list was ever re-read.
- **0.31.3** (2026-09-28): **a release can no longer go out with a failed check.** 0.31.1 was published with a person's name in it: the privacy scan caught it, but the release ran in the same command as the checks and never saw the failure. New `tools/release.sh X.Y.Z "notes"` is now the one way to release: it checks the version is the same in all four places, that everything is committed, that the tag is new, that the privacy scan is clean and that both test suites pass, each on its own, and only then pushes, tags and publishes. Any failure stops it with "Nothing was tagged or published." `--check` runs the checks alone.
- **0.31.2** (2026-09-28): the Menu-o-matiC files named a person in two places; they no longer do. Nothing else changed.
- **0.31.1** (2026-09-28): **recording marks say what kind of screen it is.** While recording, numpad + now means "a key is needed on this screen", numpad - "this screen just needs waiting for" (a logo, a loading screen, a video), and numpad * stops. Each checkpoint made from a mark is tagged menu or loading, so State-o-matiC can use it. First game set up together this way: Burnout Paradise, recorded once from launch to driving and then replayed twice from a closed game with every checkpoint matched. The recording showed what guessing had missed: "Press Any Button" appears a moment after the title, and Enter before it is ignored.
- **0.31.0** (2026-09-28): **State-o-matiC: is the game in a menu, loading, a cutscene, or gameplay?** No game announces its state, so `state_o_matic.py watch` combines signs that work from outside almost any game: black bars (a cutscene), how much of the picture moves, whether only a small patch moves (a loading icon or a menu highlight), how hard the game reads its disk (loading), and optionally whether the picture answers a key (gameplay). Screens that fool it (a menu with a 3D scene behind it, a parked car) are taught during setup with `teach`. When a Menu-o-matiC or Move-o-matiC route gets lost, the report now says what the game seems to be doing. First live run on Burnout Paradise: loading screens and the idle cinematic camera read correctly; the car screens and the parked view needed teaching. 47 checks.
- **0.30.0** (2026-09-28): **Move-o-matiC, and a setup you do together once per game.** Guessing a game's buttons wasted a session (a car tapped forward for half an hour that needed the throttle held), so every game now starts with a short setup with the person who plays it: a save past the tutorials, which button gets past each menu, the controls, an input check (`probe` holds a key and says whether a spot on screen or a mod's log changed), and then the person plays the route once while `record` notes every key and exactly how long it was held; numpad + marks a moment to check later, numpad - stops. Replays then repeat it with no pictures, waiting at each checkpoint so loading times never throw the timing off. Move-o-matiC (`move_o_matic.py`) adds held keys and camera turns to the same route files and engine. The recorder ignores keys sent by programs, so a replay is never recorded. Tried on Notepad; keyboard only for now. 33 checks.
- **0.29.2** (2026-09-28): **Menu-o-matiC now tells a crash from a slow screen, and can click.** While it waits for a screen it checks, on every look, that the game window is still there and that Windows has not marked it "Not Responding". A window that closes mid-route (a crash) is reported at once (exit 3), a game that never opens a window after launching likewise, a game "Not Responding" for a minute is exit 4, and when a wait runs out it says whether the whole picture was frozen or just showed a different screen. Slow loading is still fine: a wait keeps trying for its whole time limit. Routes can also hold mouse clicks (`click`, at a point given as fractions of the window). Tested on Notepad: a crash mid-wait, a frozen picture, a click, and a launch that never opens a window; "Not Responding" is not tested yet. 28 checks.
- **0.29.1** (2026-09-28): **Menu-o-matiC works on its first game.** Burnout Paradise Remastered now goes from a closed game to driving in the city in 150 seconds with no pictures looked at. Two fixes it needed: keys are held for 0.15 s (the game, running slowly, missed 0.07 s presses), and a wait step can say `"repress": N` to press the previous key again when a screen that is still fading in ignored it (the title screen did). `/lanes:menu` mentions both.
- **0.29.0** (2026-09-28): **Menu-o-matiC (`/lanes:menu`): games get through their own menus by themselves.** A session that tests a game walks the same intro, title screen and menus dozens of times a day, looking at a full screenshot each time. Menu-o-matiC records the way through once, as key presses plus checkpoints (a small patch of the window and a 32x32 grey fingerprint of it), and replays it with no pictures at all: waiting for a screen is plain arithmetic, so a replay costs no model tokens. Only when a checkpoint does not match does it stop and save two small pictures for the session to read. Recording is cheap too: after one half-size look, pressing a key saves only the patch that changed (anything that moves by itself is ignored), so the session reads menu lines, not screens. Keys only ever go to the named window: if Windows will not bring it to the front, nothing is sent (the first try sent a key to a web browser, which is why). Routes hold fingerprints only, never a picture of the game, so they can be shared. The tool itself (`tools/menu-o-matic/`) is plain Python any person or AI can run; the same files live in the public flat-to-vr-RE-toolkit. New test: `menu-o-matic-fixture.sh`, 23 checks, run by the smoke test (skipped without Pillow).
- **0.28.0** (2026-09-28): **every session start now checks this PC's app folders against the saved builds.** Until now nothing noticed when a PC drifted: after a week away, one PC's app folder could hold files matching no saved build at all, and nobody would know until a test gave a baffling result. A new session-start check (`hooks/builds-brief`, running the new `builds.py check`) looks at every project whose app folder this PC names in `lanes.conf`, and says so when the folder is gone, when its files match no saved build (something was swapped, or a change was never saved), or when a newer build is saved than the one this PC holds. It is silent when everything matches, silent with no `builds = ...` set, and never holds up a session start for longer than a short pull. **It names projects and build numbers only, never a folder, a machine or a person,** because what a session is told can end up in a note, a commit or a screenshot. On its first real run it found a PC whose app folder matched none of the saved builds. `LANES_BUILDS_CHECK=0` turns it off. `builds-fixture.sh` now has 37 checks, including that no folder path is ever printed.
- **0.27.1** (2026-09-27): **your own scripts can no longer quietly install into the clean game.** The day the private copy was made, four of a project's own tools (a build script's deploy step, an asset installer, a game driver, an old snapshot tool) turned out to still name the real game folder; `mint.py` and `builds.py` never write there, but a project's own scripts knew nothing of that. New `mint.py scripts <project>` reads the project repo for any script that names the clean install, in any spelling, and says where to point it instead; `mint.py check` now runs it too, so every `/lm`, `/ms` and `/pd` start sees it. A deliberate read-only use can carry a `mint-ok` comment. Logs and notes are not scanned. `mint-fixture.sh` now has 31 checks.
- **0.27.0** (2026-09-27): **keep the real game untouched, and mod a private copy of it (`/lanes:mint`).** A bug once survived three "clean" reinstalls, because verifying the game and moving the mod files out by hand both leave extra files behind; only uninstalling, deleting the leftover folder and installing again removed it. `/lanes:mint` walks you through that complete reinstall (or does the steps with you, asking before each one), records a fingerprint of every file of the clean install, and offers to make a private working copy for all your modding, checked file by file against the original. The copy stays on your PC only and carries a notice saying so, because sharing a game's files is illegal; the tool refuses to put it inside a git repository, a cloud-synced folder or the clean install itself. Once it is on, `builds.py` works in the copy and refuses to restore into the clean install, and `/lm` and `/ms` check at the start that the clean install is still clean. New tool `tools/mint.py`; new test `tools/tests/mint-fixture.sh`, 24 checks, which also proves the clean install is byte-for-byte unchanged after every command.
- **0.26.0** (2026-09-27): **every change you install becomes its own numbered version, on every PC.** Set `builds = ...` in `lanes.conf` to a clone of a private repo, and each time a session puts something into the app folder (a file in or out, a setting, a new build) it saves a full copy of everything of yours there as a new numbered folder, notes what changed and why, and pushes it at once. So you can always step back to any earlier version, and your other PC gets the same numbers: `builds.py which` tells a session which version that PC is on and whether a newer one is waiting, and `builds.py restore` puts any version back. Two PCs saving at the same moment never share a number. Files made from the game's own data are kept on the PC and never uploaded, and a restore on the other PC says exactly which ones it is missing. Nothing is ever deleted. New test: `tools/tests/builds-fixture.sh`, 29 checks.
- **0.25.2** (2026-09-26): **ideas meant for every project no longer look new.** The numbered list at the start of a session called them "fresh ideas" and said "the rest are dropped", so a reminder you had already answered on other projects read like a brand-new idea, and it was not clear that dropping one only clears it for this project. The list now counts them separately ("every-project reminder, not new") and says the drop is for this project only. - **0.21.0** (2026-09-20): before a session builds something to change a value, it now has to say where its change lands in the ORDER of what happens - and whether the thing it wants to affect has already been decided by then. - **0.20.0** (2026-09-20): the hardware tag has been split in two, because as one tag it was quietly costing you evenings. `[VR]` used to mean "needs the special hardware" - which ran together two completely different jobs: the ones where the hardware only has to be CONNECTED, and the ones where a person has to be wearing or holding it.
