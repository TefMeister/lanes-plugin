# Changes

One line per version, newest first, in plain words: what it means for someone using the plugin.
**Every version bump adds a line here.** `tools/update-check.py` reads this file to tell users
what they are missing, and the smoke test fails if the newest line does not match `plugin.json`.
**The banner is fixed artwork and never changes on a release** (since 0.24.0). A new command goes on the
front page (`README.md` at the repo root); the smoke test fails if one is missing there.

- **0.25.2** (2026-09-26): **ideas meant for every project no longer look new.** The numbered list at the start of a session called them "fresh ideas" and said "the rest are dropped", so a reminder you had already answered on other projects read like a brand-new idea, and it was not clear that dropping one only clears it for this project. The list now counts them separately ("every-project reminder, not new") and says the drop is for this project only. Nothing about how it works changed: each project answers these once, for itself, and every other project keeps its own copy until its own session answers. A new test proves exactly that.
- **0.25.1** (2026-09-26): **the two safety checks now also work when you type the long command name.** The front page tells you to type `/lanes:pd` and `/lanes:lm`, but the check that stops two `/pd` sessions at once, and the one that stops a session starting on a project another session holds, only recognised the short `/pd` and `/lm`. Typed the long way, both were skipped without a word. Both forms are caught now, and the tests cover both. The front page also gives every command its full name, and says how to give commands names you prefer.
- **0.25.0** (2026-09-26): **manual mode is now a command, `/ms`.** For when you want to do the hands-on work yourself: the session gives you a few numbered steps at a time, you do them and say "done" (or describe what you see, or paste a screenshot), and it reads the logs and writes the code in between. It never launches, drives, captures or closes the app in this lane. It takes the same claim as `/lm`, so it never works a project another session holds. Until now this lane existed only in the author's own setup, and the plugin could only describe it as "no command".
- **0.24.0** (2026-09-26): **your computer's real name is no longer written down.** An outside audit of 0.22.0 found that live claims and "only this machine can do it" reminders wrote the computer's name into the board and into commit messages, breaking the plugin's own rule that machine names are never written. Every PC now has a plain name instead: `/lanes:setup` asks what to call it, and if you do not pick one it is simply PC1, PC2 and so on. The board keeps a short `machines.txt` list so no two PCs get the same number, and a PC that never ran setup takes the next free number by itself the first time it needs one. Renaming: `tools/machine-name.py set <name>`; it refuses spaces, a name another PC has, and the computer's real name. Claims written before this version still read correctly. Also new: **a finished banner and a front page that says plainly what the plugin is** - the problem, the fix, every command in one line each, and how to start. The banner no longer carries a version or news, so it never goes stale; the old text-drawing tools are kept in `assets/banner/old-text-banner/`. New test: `tools/tests/machine-label-fixture.sh`, 15 checks, which plays two PCs on one board and searches every file and commit for the real name.
- **0.23.1** (2026-09-26): a project is only treated as paused, and left out of ideas meant for every project, when its board has a line STARTING with `⏸️ **PAUSED`, the form the board docs describe. 0.23.0 also counted an old history line that merely mentioned a pause, so a project that had been paused once and then resumed would have stopped getting those ideas. Checked against 38 real boards: the same answer as before on every one.
- **0.23.0** (2026-09-26): **ideas are filed without anyone asking.** Keep a private ideas repo (a ready-made one is in `template-ideas/`) and write ideas into its `DUMP.md` whenever they come - from GitHub on a phone is fine - as `[project; part] the idea`. A new session-start check notices when something is waiting and has the session file it FIRST, before its other work, with the new `/lanes:ideas`: your words copied verbatim into a permanent `inbox/` record, each idea sorted onto its project's page and tagged, and the dump emptied again. The emptying can never lose an idea: `tools/ideas.py clear` only removes a line that is already saved word for word in the inbox, so anything typed while a session is filing stays put. Filed ideas are then copied into each project's own repo, and the next `/pd` or `/lm` on that project opens with them as a numbered list; answer with the numbers to keep and the rest are dropped from that project (their words stay in the inbox). Set `ideas = ...` in `lanes.conf` to switch it on; with nothing set it stays silent. New test: `tools/tests/ideas-fixture.sh`, 28 checks, run by the smoke test.
- **0.22.0** (2026-09-24): **first public release**, in its own repository (`TefMeister/lanes-plugin`), still an early version. New: **one naming rule for every session** - in anything saved or published, the person at the machine is "User", unless they choose a display name in `/lanes:setup` (the first thing it now asks); their real name, login, e-mail, machine names and home-folder paths are never written. A session-start hook puts that rule in front of every session, so nothing has to remember it. The old word list that shipped inside the plugin is gone (publishing it published its words); extra private words now live only on your own machine, in `~/.claude/lanes/never-publish.txt`. Also: an optional tool that removes copy protection is no longer in the tool catalog, and the line-ending rules now actually cover the hook scripts.
- **0.21.1** (2026-09-21): when a new version is out, the question now always arrives on its own line, in the same words and with a bell in front of it - "🔔 New plugin update available! Would you like to install it now?" - so it stands out from the rest of the reply and can be found without reading everything around it.
- **0.21.0** (2026-09-20): before a session builds something to change a value, it now has to say where its change lands in the ORDER of what happens - and whether the thing it wants to affect has already been decided by then. This sounds too obvious to be a rule, and it is here because skipping it cost four builds and five rounds of live testing in one evening while a correct trace sat in the notes the whole time. A weapon scattered its shots from the hip; the function carrying that scatter was found and a fix made its two numbers equal. The fix worked perfectly and changed nothing - the log read "11.188 -> 0.000 APPLIED" and the shots stayed random - because the session's OWN trace, taken hours earlier, showed the projectile was already finished by the time that function ran. It reports the scatter; it does not decide it. Nothing was missing or unclear: the evidence was read, recorded, and then built on as though the last step were the first. Three companions ship with it, each from the same evening. A test must be able to tell "no effect" from "wrong choice", so a lever should measure, act, then RE-MEASURE and log both numbers - two attempts failed with identical symptoms and nobody could tell which had happened, and each wrong guess cost a person another trip to the keyboard. A guard must not be more dangerous than the thing it guards: a safety check around a 16-byte write into memory that had been read successfully for an hour reached into the framework's type metadata through a cast the framework's own header calls invalid, and crashed the application before the write it protected ever ran - so validate the DATA you are about to touch, not the framework's description of it, and make "off" genuinely inert, because that build did its fatal checking before it ever read whether the feature was enabled. And the bottleneck is usually reading what you already collected: five times in three days the answer was in gathered evidence, including a field on line 73 of a dump that was being quoted from line 71 - volume hides things, and a summary written by the session that gathered the data inherits its blind spot.
- **0.20.0** (2026-09-20): the hardware tag has been split in two, because as one tag it was quietly costing you evenings. `[VR]` used to mean "needs the special hardware" - which ran together two completely different jobs: the ones where the hardware only has to be CONNECTED, and the ones where a person has to be wearing or holding it. Only the second needs you, but the board could not tell them apart, so every hardware-shaped job queued up behind you being free - including work a session could have done alone overnight. Now `[VR CLAUDE]` means plug it in and walk away, and `[VR USER]` means a person must actually be using it. When in doubt the rule is to write `[VR USER]`, because the two mistakes are not equal: calling a person-job a session-job sends the session off to answer a question it physically cannot, and it returns a confident number that means nothing. A bare `[VR]` is now reported as a violation rather than silently migrated, because which of the two it is cannot be guessed. ⚠️ One defect was found and fixed while making this change, and it is the reason the split is safe: the row parser takes the first word of a tag, so that a row can carry a qualifier like `[PD @home]` - which would have reduced BOTH new tags back to "VR", silently, leaving a board that looked perfectly healthy while telling sessions they could work alone on jobs that need a person present. The two-word names are now matched before that split, and the test fixture carries both tags so it cannot regress.
- **0.19.0** (2026-09-20): the headings in a session's reply now carry fixed icons, the way the gate and model box has since 0.5.1 - 🔧 what I did, 🎯 what it means for you, ❓ what I need from you, and ⚠️ worth knowing for anything that turned up outside the job. The box was given icons because people skim; the rest of the reply was left plain, so an answer opened with three or four bare headings that all looked alike and the reader had to read each one to find the part that actually wanted something from them. Fixed icons make the reply navigable without being read end to end - a reader who has seen two of them jumps straight to ❓. They are fixed on purpose: an icon chosen fresh each time is decoration and carries no information. The sections stay the same length as before, because an icon is not room to write more.
- **0.18.0** (2026-09-20): when a job needs YOU - a wearer, a hand on a controller, an eye on the screen - the session now hands it over as numbered steps written BEFORE the run, instead of a paragraph describing what it would like to find out. What goes in them is fixed: what must already be true before step 1, one action per step, a baseline measured before any variant, the question in your words and what to IGNORE, what each failure looks like and what to do about it, permission to answer vaguely ("about halfway up" is a real measurement from someone holding a controller), and how to put it back. The steps are also left as a plain file beside the thing being tested, because nobody mid-test can scroll back through a conversation for step 12. The reason this is a rule and not a style note: writing the steps out is a TEST OF THE TOOLING. It is how a restore script was caught undoing only one of the two settings the variants changed - the baseline would then have been secretly identical to the variant, the two would have given the same answer, and the session would have concluded "no difference" with nothing in any log to show why. The scripts ran cleanly and reported success; the defect was visible only from the point of view of a person following the steps in order.
- **0.17.0** (2026-09-19): the tag check's fix from 0.16.0 is now actually IN the plugin, and the reason it was not is fixed too. The plugin ships its own copy of the sweep scanner, deliberately reworded and generalised so it works for anyone - and that legitimate difference hid a real one: a fix made to the private copy was never ported here, and nothing noticed, because the two files were already hundreds of lines apart. "They differ" carried no information. Ported, and the plugin now also ships the check-3b fixture it had been missing entirely - it had the scanner and no proof that check worked. Also carried across the reasoning behind a REJECTED fix, so nobody re-proposes it: classifying on a window of lines instead of one line was written, tested, and thrown away, because in dense text a correction word near an unrelated tag marks that tag as already-fixed - a false negative that HIDES a real defect. A noisy check is annoying; a quiet one is dangerous, and when a check must choose it errs toward noisy. The cure is author-side and free: keep a quoted tag and its correction word on the same line.
- **0.16.0** (2026-09-19): a correction can now be checked for whether the thing it says is WRONG is still there. This exists because one was not: a research pass found a sentence in a project's notes was false and filed a correction; two later sweeps re-flagged it; fifteen days and four flags after the first, the sentence was still there, still false, and still being used as the stated reason for a live design decision. Nobody ignored it - a correction looks exactly like a contribution when you are draining a folder of files, volume hides it, and "this is N days old" says nothing about whether the claim is still wrong. So a correction aimed at a curated document now carries one more line - `Still-wrong: <file> :: <the exact string that must go>` - and `tools/inbox-correction-scan.py` reads the target and says whether it is still there. That changes the question from "has anyone drained this?", which competes with every other pending file, to "is the falsehood live?", which is a fact you can escalate. A drop that says what is wrong, verbatim, is worth more than one that only says what is right. Also fixes a one-word gap in the off-vocabulary tag check: its list of correction words had `retagged` and `now reads` but not `became`, so a lane that correctly documented a fix earned a permanent false positive for it - the same self-reinforcing error an earlier split was built to remove. `tools/tests/inbox-correction-fixture.sh`, 12 checks, 0 failed. The tool is inert until drops adopt the convention, and reported zero on the day it shipped; that is not evidence of a clean estate.
- **0.15.0** (2026-09-19): a standing rule can now be checked for whether it can actually **reach** the session that needs it. This exists because one failed: a design instruction was filed correctly, in the right repo, with the user's own words quoted - and fifteen days later they had to give it again, because in between nobody applied it. Three mechanical reasons, none of them anyone's fault: it lived only in a file the harness does not auto-load, so reading it depended on somebody deciding they needed it; its heading was a nice phrase containing none of the words you would search for when the decision is actually in front of you; and the same subject later picked up a second full copy elsewhere, free to drift. `tools/rule-reach-scan.py` reports those three separately and exits non-zero. The general point is not about this estate: an instruction is filed in the words it was **given** in, and those are rarely the words it will be **looked for** in - the filing has to translate. `tools/tests/rule-reach-fixture.sh` plants each fault and asserts the scanner names it, including the literal heading that started this, and asserts a good heading is left alone so it cannot pass by flagging everything. 8 checks, 0 failed.
- **0.14.1** (2026-09-18): the reminder tool no longer writes into the wrong copy of your board. If you keep one clone per lane, `owed.sh` was reading the board path out of your config before it looked at where it was actually running, so whichever lane raised a reminder, the file landed in the clone the config named — in practice, in another live session's working tree, uncommitted. It now prefers the clone it belongs to, then the clone you are standing in, and only then the config, which is still what the session-start greeting uses. Nobody with a single clone will notice any difference. The smoke test now covers all three, because every existing assertion pinned the board explicitly and so none of them could ever have caught this.
- **0.14.0** (2026-09-18): if you work on more than one computer, anything that can only be done on the *other* one is now queued **for that machine** instead of sitting in a note both machines read and neither owns. `tools/owed.sh add HOME "<title>"` raises one; the machine it is addressed to is greeted with it at session start, and nobody else is; it clears when that machine actually does it. One file per item, so two machines raising work in the same minute cannot clash. The tool never commits, it refuses to address the machine you are sitting at, and clearing takes one exact filename — never a pattern, because a pattern can delete an item another session raised seconds ago and left uncommitted.
- **0.13.0** (2026-09-18): the maintainer's own name is gone from every file, and a new `tools/scrub-names.txt` lets you list the words that must never be published from your copy - your handle, your other machines - so the check enforces them instead of you remembering. The GitHub account name is deliberately not on that list: an install command cannot work without it. New `HISTORY.md` tells the story the commit log used to, so a repo can be re-created clean without losing how it was built.
- **0.12.3** (2026-09-18): re-creating the repo no longer wipes out your reader run count. The count asked git when the reader shipped, which answers about THIS repo - so in a repo started fresh, every file looks added on day one and the count silently drops to zero. It reads the recorded date first now, git only if that is missing. Measured on a simulated fresh repo: 37 runs kept, where the old way reported 0.
- **0.12.2** (2026-09-18): a new `scrub-scan` check refuses to let the plugin ship anything that identifies a real person - a home folder naming a real account, a real email address, a session id, or the machine's own name - because the old way of checking that was a line in a checklist telling someone to grep, and in six weeks nobody did. It found a captured debug file carrying a username, a home path and a slice of a personal settings file. Anything deliberate can be marked, and every marked line is listed back so the exceptions cannot grow quietly.
- **0.12.1** (2026-09-18): `/lanes:update` stops answering "you are up to date" when it has not actually looked. It used to read the version out of whichever copy of itself it was run from, so run from a repo checkout it reported that repo's version and found no marketplace at all; and when your marketplace is a local folder it now pulls that folder first, because the installer reads the folder's files while the check reads GitHub - so a release pushed from elsewhere installed nothing and still said it had worked.
- **0.12.0** (2026-09-18): every lane now tells you which model the job it just picked actually needs, BEFORE doing the work rather than only in its final report - so you can switch and re-run in ten seconds instead of finding out afterwards that the strongest model was spent on clerical work. If the running model is too weak for the job it stops and waits; if it is stronger than needed it says so and carries on, because pausing a session whose owner is away costs more than the tokens it saves.
- **0.11.2** (2026-09-18): setup asks Blender whether the link actually works before offering to set it up, so anyone who already has it connected is told that instead of being walked through steps they finished long ago.
- **0.11.1** (2026-09-18): setup no longer claims a tool is missing when it is simply installed somewhere else — 7-Zip is found wherever Windows recorded it, and Steam games are found in every library folder, not only the one on C:.
- **0.11.0** (2026-09-17): `root-sync.sh` keeps every lane's copy of your repos complete; `/pd`, `/gr`, `/sr` and `/gs` run it first, so a newly added project is never silently left out of a sweep.

- **0.10.2** (2026-09-17): the banner has three info panels (what is new, every lane command, how to install), and the test fails if a command is missing from it.
- **0.10.1** (2026-09-17): the plugin has a banner; its version number and notes are rebuilt on every release, and the smoke test checks they match.
- **0.10.0** (2026-09-17): tells you when a newer version of the plugin is out, lists what changed, and updates itself if you say yes (`/lanes:update`).
- **0.9.0** (2026-09-17): first-run guided setup of the optional tools (`/lanes:setup`), with official links, including Blender + Blender MCP and Ghidrust.
- **0.8.0** (2026-09-17): a generator for the small test file placed next to an app, with a fix for a Windows quirk that crashed apps at start-up.

- **0.6.4** (2026-09-16): `/lm` quits an app through its own menu instead of killing it, so saves are not corrupted.
